# Verification record and remaining boundaries

This project was improved and tested in an isolated copy before applying a finite reviewed delivery to its original folder. Existing account data, transaction data, compiled artifacts, and Git history are not included in the delivery manifest. The delivery cites a central implementation report and project manifest `d0778f38946f`. Neither is in this repository, which has a single commit, so treat those references as provenance you cannot check from here.

**Re-run 2026-10-06 (docs review).** Compiling `src` and `test` with Microsoft OpenJDK 17.0.10 (`--release 17 -Xlint:all`) into a temporary folder and running `bankapp.RegressionTests` printed `RESULT passed=28 failed=0`. The 28 is a count of `test(...)` calls in `test/bankapp/RegressionTests.java`. The same review reproduced, as CLI processes, findings 1, 2, 3, 5 and 7 in [06](06-SOLUTIONS-AND-REVIEW.md): exit code 0 on a corrupt start, `1e3` accepted, a lost update between two sessions, an unreconciled edited balance, and a list-only session rewriting the file. It also ran the practice check file in [05](05-PRACTICE.md): 1 pass and 5 expected failures on the delivered code.

The original delivery compiled with the same JDK and flags.

Six initial regression checks failed against the original source, covering escaped mutable state, retained caller references, duplicate account identity, orphan history, silent amount rounding, and invalid negative balances. The final suite passed **28 Java regression tests**. These include all outward account-copy paths, snapshot isolation, model guards, duplicate transaction IDs, transfer reference validation, conservation and paired history, rejected transfer preservation, 64 competing withdrawals, concurrent snapshot capture, rename behavior, restricted deletion, legacy migration, corruption and truncation rejection, real temporary-file replacement, and failure cleanup.

The separate orchestration script passed **seven CLI scenarios in new Java processes**, for **35 checks total**. It verified create/reload, persisted balances and paired transfer history, precision rejection, rename persistence, protected deletion and confirmation, EOF during an incomplete account prompt, and byte preservation on corrupt startup. The project runner executes the 28 Java cases. The seven-scenario CLI script and its logs were kept outside this repository and are not available here. The practice check file in 05 covers comparable CLI ground and runs from a clean clone.

These results establish local simulator behavior. No HTTP server, browser, database, authenticated owner model, external bank connection, or real transfer was involved. The synchronization boundary is one `BankService` instance. Two independent services or processes can still race when saving the same file, and the file format has no compare-and-swap version protocol.

Commands mutate service memory before the CLI saves. Success is printed only after saving, and IOException ends the CLI, but the service itself has no transactional persistence dependency or rollback mechanism. Power-loss durability and filesystems without atomic replacement support were not established. Unsupported atomic replacement fails visibly; the implementation does not silently fall back to a partial overwrite.

Loaded data is checked for valid fields, duplicate IDs, references, header, and record counts. It is not fully reconciled against historical balances, and the footer is not a checksum or tamper-proof signature. Transfer records still lack a shared operation ID. Those limitations are explicit practice topics rather than hidden claims of completeness.

Migration leaves legacy files unchanged and makes the first successfully written snapshot authoritative. Old application binaries do not understand that new authority; use the delivered source/runner and do not alternate old and new programs against the same directory. The CLI currently reports load and save failures as text and still exits with status 0 (`App.java:34-40`). Review these boundaries before adapting this foundation into a multi-user CRUD web application.
